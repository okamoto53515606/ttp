## 結論

**EC2 は普通にできます。Fargate も可能ですが条件付き（ECS Exec 前提）** です。Session Manager の「ポートフォワーディングセッション」は、**ローカル PC 上に TCP リスナを開いて、それを SSM の WebSocket 経由でリモートのポートに繋ぐ**だけの仕組みなので、Tera Term からは「localhost のそのポート」に SSH すれば繋がります。

## 仕組み

```mermaid
flowchart LR
    TT["Tera Term<br/>localhost:10022"] -->|TCP| SP["session-manager-plugin<br/>(ローカルで待受)"]
    SP -->|WebSocket over 443<br/>アウトバウンドのみ| SSM["SSM エンドポイント"]
    SSM --> AG["SSM Agent<br/>(EC2 / コンテナ内)"]
    AG -->|TCP localhost:22| SSHD["sshd"]
```

ポイントは **インバウンド 22 番の開放が不要**、**踏み台ホストも不要**、**通信はすべてアウトバウンド 443** という点です。認証は IAM（`ssm:StartSession`）で行い、SSH の鍵はトンネルの中を通るだけです。

## EC2 の場合

### 前提条件

| 項目 | 内容 |
|---|---|
| SSM Agent | インスタンスに導入済み（Amazon Linux/Windows AMI は標準搭載） |
| IAM | インスタンスプロファイルに `AmazonSSMManagedInstanceCore` |
| ネットワーク | SSM エンドポイントへ 443 到達可能。閉域なら VPC エンドポイント `ssm` / `ssmmessages` / `ec2messages` を作成 |
| ローカル | AWS CLI + **Session Manager plugin**（これが無いと動かない。一番のハマりどころ） |
| ローカル IAM | `ssm:StartSession` 権限 |

### トンネルを張る

```powershell
aws ssm start-session `
  --target i-0123456789abcdef0 `
  --document-name AWS-StartPortForwardingSession `
  --parameters portNumber=22,localPortNumber=10022
```

`Port 10022 opened for sessionId ...` と出れば待受開始です（このウィンドウは閉じない）。

### Tera Term 側

- ホスト：`localhost`、TCP ポート：`10022`
- サービス：SSH / SSH2
- ユーザ名：`ec2-user` など（インスタンスの OS に合わせる）
- 認証：「公開鍵」で `.pem` を指定、またはパスワード

つまり **Tera Term の設定は「ホスト名だけ localhost に変える」だけ**です。

### 毎回が面倒な件 → バッチ化

```bat
@echo off
start "SSM Tunnel" aws ssm start-session --target i-0123456789abcdef0 ^
  --document-name AWS-StartPortForwardingSession ^
  --parameters portNumber=22,localPortNumber=10022
timeout /t 3 >nul
start "" "C:\Program Files (x86)\teraterm\ttermpro.exe" localhost:10022 ^
  /ssh /2 /auth=publickey /keyfile="C:\keys\my-key.pem" /user=ec2-user
```

これをショートカットにしておけばワンクリックで繋がります。`--parameters` は JSON ではなく `key=value` 形式で書けるので、`bat` のエスケープ地獄を避けられます。

> 補足：OpenSSH を使うなら `~/.ssh/config` に `ProxyCommand aws ssm start-session --target %h --document-name AWS-StartSSHSession --parameters portNumber=%p` を書く手もありますが、**Tera Term は任意の ProxyCommand に対応していない**ので、Tera Term なら上記のローカルポート方式が素直です。

## Fargate / ECS の場合

可能ですが、**`AWS-StartPortForwardingSessionToRemoteHost` を使う必要があり、`host` に `localhost` を指定**します（ECS タスクでは単純な `AWS-StartPortForwardingSession` は使えません）。

前提：`enableExecuteCommand` を有効化したタスク、タスクロールに `ssmmessages:CreateControlChannel` / `CreateDataChannel` / `OpenControlChannel` / `OpenDataChannel`、SSM Agent 3.1.1374.0 以上（Fargate はプラットフォームバージョン 1.4.0 以降）。

```powershell
# runtimeId を取得
aws ecs describe-tasks --cluster my-cluster --tasks <task-id> `
  --query "tasks[0].containers[0].runtimeId" --output text

# トンネル
aws ssm start-session `
  --target ecs:my-cluster_<task-id>_<runtime-id> `
  --document-name AWS-StartPortForwardingSessionToRemoteHost `
  --parameters '{"host":["localhost"],"portNumber":["22"],"localPortNumber":["10022"]}'
```

ただし実務上は、**Fargate コンテナに sshd を入れる必要がある**のであまり嬉しくありません。Fargate なら素直に ECS Exec のシェルで十分なことが多いです。

```powershell
aws ecs execute-command --cluster my-cluster --task <task-id> `
  --container app --interactive --command "/bin/sh"
```

## よくあるハマりどころ

- **Session Manager plugin 未インストール** → `aws ssm start-session` が「plugin not found」で失敗
- **20 分のアイドルタイムアウト** → Session Manager の設定で延長可能（最大 60 分）。Tera Term 側の keepalive も併用
- **ローカルポート重複** → 前回のセッションが残っていると `bind failed`
- **閉域網** → VPC エンドポイント不足（特に `ssmmessages`）
- **`AWS-StartPortForwardingSession` と `AWS-StartSSHSession` の混同** → 前者は Tera Term 用トンネル、後者は `ssh` コマンドの ProxyCommand 用

## セキュリティ上の注意

- SSM 権限を持つ人は実質シェルに入れるので、**IAM で対象インスタンスを絞る**（`ssm:StartSession` のリソース ARN 指定）
- **ポートフォワード/SSH 経由のセッションは Session Manager のログに残りません**（TLS 内でさらに SSH 暗号化されるため）。監査は CloudTrail の `StartSession` で行うことになります
- 逆に、SSH 鍵の配布や Security Group の 22 番開放が不要になるのは大きなメリットです

要するに「面倒」の正体はほぼ **plugin の有無と、毎回コマンドを打つ手間**なので、バッチ＋ショートカットで解決するのが実用的です。

今やっている「Session Manager で接続」は、SSH でも Telnet でもありません。

```
通常の SSH :  Tera Term ──SSH──> sshd ──> shell
Session Mgr:  aws CLI ──SSM独自プロトコル(WebSocket)──> SSM Agent ──> shell
```

## ポートフォワードはプロトコルを変換しない

`session-manager-plugin` がローカルに開くのは、**ただの生の TCP 中継ポート**です。

```mermaid
flowchart LR
    TT["Tera Term<br/>(SSHクライアント)"] -->|"SSHプロトコル<br/>をそのまま流す"| P["localhost:10022<br/>(生TCPの中継)"]
    P --> AG["SSM Agent"]
    AG -->|"localhost:22 へ<br/>生TCPを流す"| S["sshd"]
```

なので：

- リモート 22 番に **sshd が居なければ、「Connection refused」やハンドシェイク失敗**になる
- 逆に言えば、**22 番に限らず何でも中継できる**（RDP 3389、MySQL 3306、HTTP 80、VNC 5900 など）

## 目的別の選び方

| やりたいこと | sshd | 方法 |
|---|---|---|
| シェルに入りたいだけ | 不要 | `aws ssm start-session --target i-xxx`（今のやり方） |
| **Tera Term の UI でシェルを使いたい** | **必要** | sshd を導入 → ポートフォワード 22 → Tera Term で `localhost:10022` に SSH |
| Windows にリモートデスクトップ | 不要 | ポートフォワード 3389 → `mstsc /v:localhost:13389` |
| DB にローカルクライアントで繋ぐ | 不要 | `AWS-StartPortForwardingSessionToRemoteHost` で 3306 など |
| Web UI をローカルブラウザで見る | 不要 | 80/443 をポートフォワード |

**Tera Term を使いたい理由が「ログ取得・マクロ・キー割当・複数タブ」なら、sshd を入れるのが一番素直**です。

## sshd を入れる手順（Amazon Linux 2023 の例）

```bash
# SSM のシェルで実行
sudo dnf install -y openssh-server
sudo systemctl enable --now sshd
sudo systemctl status sshd
```

Ubuntu なら `sudo apt install -y openssh-server`。

- **Security Group の 22 番開放は不要**（トンネルは SSM Agent 経由なので）
- 認証は既存の鍵ペア（`~/.ssh/authorized_keys`）か、パスワード認証を有効化
- 公開鍵を入れたいだけなら、SSM シェルから `authorized_keys` に追記すれば済みます

## 補足：Telnet で繋ぐケース

Tera Term の Telnet を使うのは、リモートに **telnetd が居る場合だけ**です（ネットワーク機器、古い UNIX、特定のアプリなど）。EC2 の Linux には通常 telnetd は入っていないので、今回の用途では出番はありません。また Telnet は平文なので、SSM トンネルで暗号化されていてもホスト間では推奨されません。

## 本命の妙案：ttp を「接続プロバイダ方式」に拡張する

正直、**ttp を拡張するのが一番筋が良い**です。理由は、今の ttp が既に必要な部品を持っているからです。

| 既にある | SSM/ECS で必要 |
|---|---|
| マスターパスワード + AES 暗号化ストア | AWS 認証情報・秘密情報の保管 |
| 接続先一覧の GUI + ワンクリック起動 | 同じ UX |
| `ttpmacro.exe` の自動検出 | `aws.exe` / `session-manager-plugin.exe` の検出（同じパターンで書ける） |
| 環境変数 → 外部プロセス起動 | `wt.exe` → `aws ecs execute-command` に差し替えるだけ |
| 自動ログ | ※ここだけは代替が必要（後述） |

つまり **「起動先を Tera Term から Windows Terminal に差し替える」**のが本質で、構造変更は小さく済みます。

### 認証情報の扱い（ここが一番の設計ポイント）

| SSO | プロファイル名のみ | ◎ 秘密情報ゼロ。必要なら `aws sso login --profile x` を ttp から起動 |
| assume role | プロファイル名のみ | ○ |
| 長期キー | secret + session_token を既存 AES で暗号化 | △ やむを得ない場合のみ。環境変数に積むので `--debug` ログに注意 |

### ログの扱いだけは注意（Tera Term の `logopen` に相当するものが無い）

- **ECS**：クラスタの `executeCommandConfiguration` で CloudWatch Logs / S3 へ自動保存

「ログはクラウド側、ファイルは端末から手動エクスポート」という割り切りが現実的です。

## 「接続可能」の判定ロジック

### EC2

`ssm describe-instance-information` は **SSM エージェントがオンラインのインスタンスしか返しません**。つまり「SSM Agent 入ってる／ネットワーク到達できてる／IAM ロールが正しい」を全部満たすものだけがここに出ます。

```powershell

  --query "InstanceInformationList[?PingStatus=='Online'].[InstanceId,ComputerName,PlatformName,LastPingDateTime]"
```

- 名前（Name タグ）が欲しいので `ec2 describe-instances`（`instance-state-name=running`）と突き合わせる
- **出てこない＝つながらない**なので、グレーアウト表示も自然に作れる

### Fargate / ECS

条件は 2 つ：**タスクで ECS Exec が有効** かつ **`ExecuteCommandAgent` が RUNNING**。

```mermaid
flowchart TD
    A["list-clusters"] --> B["describe-services<br/>(enableExecuteCommand を見る)"]
    B --> C["list-tasks --desired-status RUNNING"]
    C --> D["describe-tasks<br/>(100件/コール)"]
    D --> E{"enableExecuteCommand == true<br/>かつ<br/>ExecuteCommandAgent == RUNNING"}
    E -->|Yes| F["一覧に表示（接続可）"]
    E -->|No| G["グレー表示 or 非表示"]
```

**最適化のコツ**：`describe-services` で `enableExecuteCommand` が false のサービスはタスクを describe しなくて済みます。これで API コールが桁で減ります（`run-task` で立てた単発タスクだけは個別に describe が必要）。

### 1. boto3 か、`aws` CLI か

| | boto3（アプリ内で API 直叩き） | `aws` CLI を subprocess |
|---|---|---|
| 速度 | ◎ プロセス起動なし、ページングも制御可 | △ 1 コール 0.5〜1.5 秒 |
| exe サイズ | ▲ +30〜40MB（botocore） | ○ 増えない |
| 依存 | plugin のみ | `aws.exe` + plugin |
| 実装量 | やや多い | 少ない（JSON パースだけ） |

**おすすめ：一覧取得は boto3、セッション起動は `aws` CLI**。一覧は頻繁に叩くので速さが効き、起動は CLI に任せると `session-manager-plugin` の呼び出しを自前で書かずに済みます。exe サイズが気になるなら `--exclude-module` で未使用サービスを削るか、全部 CLI に寄せられます。

### 2. 認証情報のリスク（ここは正直に言うべき点）

3 項目だけで済む＝**長期アクセスキーを持つ**ということなので、設計で緩和します。

- IAM ユーザーは専用にして、権限を最小化

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": [
        "ec2:DescribeInstances", "ecs:ListClusters", "ecs:ListServices",
        "ecs:ListTasks", "ecs:DescribeTasks", "ecs:DescribeServices",
        "ecs:ExecuteCommand", "ssm:DescribeInstanceInformation", "ssm:StartSession"
      ], "Resource": "*" },
    { "Effect": "Allow", "Action": [
        "ssmmessages:CreateControlChannel", "ssmmessages:CreateDataChannel",
        "ssmmessages:OpenControlChannel", "ssmmessages:OpenDataChannel"
      ], "Resource": "*" }
  ]
}
```

- **保存はメモリ上と既存の AES ストアのみ**。ログ・例外メッセージ・子プロセスのコマンドラインに出さない（コマンドライン引数にキーを渡すとタスクマネージャで見えます）
- 子プロセスへは `AWS_ACCESS_KEY_ID` 等の環境変数で渡す（既存の `TT_TTL_PASSWD` と同じ方式）
- MFA 必須ポリシーの場合に備えて、**MFA コード入力 → `get-session-token`** の余地を残す
- 将来 profile / SSO を足せるよう、`auth_mode` を 1 フィールド持たせておく（`static` / `profile` / `sso`）

> 補足：1 つのキーを複数人で共有すると CloudTrail で個人を特定できなくなります。配布するなら各自の IAM ユーザー発行を推奨。

### 3. tkinter のフリーズ対策

## 1. MFA の話

AWS の IAM ユーザーに **「MFA を必須にする」ポリシー**を敷いている場合の話です。

```json
{ "Effect": "Deny", "Action": "*", "Resource": "*",
  "Condition": { "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" } } }
```

こういうポリシーがあると、**アクセスキー＋シークレットだけでは API が `AccessDenied` になります**。MFA コードを添えて一時クレデンシャルに交換する必要があります。

```powershell
aws sts get-session-token `
  --serial-number arn:aws:iam::123456789012:mfa/okamo `
  --token-code 123456 `
  --duration-seconds 43200
```

つまり MFA 運用なら、ttp に **6 桁コードの入力ダイアログ**が必要になります（有効期限は既定 12 時間なので、実質 1 日 1 回）。

| 状況 | 対応 |
|---|---|
| IAM ユーザーに MFA を強制していない | **不要**。今の設計（キー＋シークレット＋リージョン）でOK |
| MFA を強制している | コード入力ダイアログ + `get-session-token` が必須 |

## 2. 依存パッケージの脆弱性対応は頻繁になるか

**「頻度は上がるが、実務負担は小さい」**が結論です。理由を分けて説明します。

### 増えるパッケージ

`boto3` を入れると以下が付いてきます（`uv.lock` で固定されます）。

```
boto3 → botocore → urllib3, jmespath, python-dateutil, s3transfer
```

現在の依存は `cryptography` 1 個だけなので、**1 → 7 個**になります。

### 「更新の頻度」と「脆弱性の頻度」は別物

| パッケージ | リリース頻度 | CVE の頻度 |
|---|---|---|
| botocore | **ほぼ毎日**（サービスモデル追加） | ほぼ無し |
| boto3 | 週 1 回程度 | ほぼ無し |
| **urllib3** | 数か月に 1 回 | **たまに出る**（これが本命） |
| jmespath / python-dateutil | 年数回 | ほぼ無し |

つまり **Dependabot の通知は毎日うるさくなるが、実際に対応が必要なセキュリティ修正は年 0〜2 回**というのが実態です。しかも urllib3 の CVE は「攻撃者が制御する URL へリダイレクトさせる」系が多く、**接続先が AWS エンドポイントに固定されている本アプリでは実質的な影響はほぼありません**。

### 実務的な運用案

```bash
# 月1回これだけ
uv lock --upgrade
uv sync
uv run python -m ttp   # 動作確認
uv run python build.py # exe ビルド
```

- 対応コストは **月 30 分程度**
- botocore の日次更新は**追わない**（`uv.lock` で固定されているので勝手には上がらない）
- GitHub の Dependabot を使うなら、**botocore の patch 更新は ignore** にして、`urllib3` / `cryptography` の **security alert だけ拾う**設定にする

```yaml
# .github/dependabot.yml のイメージ
updates:
  - package-ecosystem: "uv"
    schedule: { interval: "monthly" }
    groups:
      aws-sdk: { patterns: ["boto3", "botocore", "s3transfer", "jmespath"] }
    ignore:
      - dependency-name: "botocore"
        update-types: ["version-update:semver-patch"]
```

### 気にすべき副作用（脆弱性よりこっち）

1. **exe サイズ増**：botocore のサービスモデルで **+40〜60MB** 程度。PyInstaller のフックは用意されているので動きますが、ビルド時間も伸びます
2. **ビルドの再現性**：`uv.lock` を必ずコミット（今もありますね）
3. **オフライン動作用の証明書**：`certifi` 系の更新も付いてくるが、これは自動で問題にならない

### 選択肢の比較

| 方式 | 依存増 | 更新負担 | 一覧の速度 | exe サイズ |
|---|---|---|---|---|
| **boto3**（採用） | +6 | 月 30 分 | ◎ | +40〜60MB |
| `aws` CLI を叩く | 0 | ほぼ無し（AWS CLI 側の更新は別） | △ コール毎に 1 秒 | 変化なし |
| botocore のみ | +5 | 同上 | ◎ | 同上 |

boto3 を選ぶのは妥当です。**「毎日通知が来るのを無視できる仕組み（グループ化 + ignore）を最初に用意する」**ことだけセットでやっておけば、負担にはなりません。

## 結論：**やる価値あり。ただし「AWS CLI を外す」話であって、「プラグインは外せない」**

Session Manager の通信路（WebSocket + 独自バイナリプロトコル）を実装しているのが `session-manager-plugin.exe` なので、これだけは代替できません。逆に AWS CLI は「boto3 で API を叩いて、プラグインを起動するだけの薄いラッパー」なので、置き換え可能です。

| | サイズ | インストール | 管理者権限 |
|---|---|---|---|
| AWS CLI v2 | **約 250MB** | MSI | 必要 |
| Session Manager プラグイン | 10〜20MB | MSI | 必要 |
| boto3（既に同梱済み） | 約 40MB | 不要 | — |

つまり **2個 → 1個、270MB → 20MB** になり、ポータビリティ的にはかなり効きます。

## 仕組み（aws-cli の実装を確認しました）

aws-cli がやっているのは、要するにこれだけです。

```
session-manager-plugin <session-json> <region> StartSession <profile> <ssm-params-json> <endpoint>
```

**SSM の場合**
```python
resp = ssm.start_session(Target="i-xxx")
# resp = {SessionId, TokenValue, StreamUrl}
# ssm-params-json = {"Target": "i-xxx"}
# endpoint = https://ssm.ap-northeast-1.amazonaws.com
```

**ECS Exec の場合**
```python
resp = ecs.execute_command(...)          # -> resp["session"]
# ssm-params-json = {"Target": "ecs:{cluster}_{taskId}_{runtimeId}"}
# endpoint = https://ecs.ap-northeast-1.amazonaws.com
# operation は同じく "StartSession"
```

`runtimeId` は `describe_tasks` の `containers[].runtimeId` から取れます（既に一覧取得で describe_tasks を呼んでいるので追加コストゼロ）。

もう一点、aws-cli は新しいプラグイン向けに **セッショントークンを環境変数 `AWS_SSM_START_SESSION_RESPONSE` で渡す**方式に切り替えています。これを真似すれば、トークンがプロセス一覧に出ません（今の CLI 方式より安全）。

実装量は **100〜150 行程度**です。

## 選択肢の比較

| 案 | インストール | ポータブル度 | 保守 | リスク |
|---|---|---|---|---|
| **A. 現状（CLI + プラグイン）** | 2個 / 270MB | △ | 少 | 低（公式手順どおり） |
| **B. boto3 + プラグイン（推奨）** | 1個 / 20MB | ○ | 少 | 中（プラグイン引数は非公開IF） |
| **C. プラグインも同梱** | **0個** | ◎ | 中 | 中〜高（同梱物の管理） |

### B を推す理由

- インストールが 1/13 のサイズになる。CLI は Python 一式と全サービスのモデルを抱えているので無駄が大きい
- エラーの日本語化・タイムアウト・認証の扱いを自分でコントロールできる（今は CLI の出力頼み）
- boto3 は既に入っているので追加依存ゼロ
- CLI のコールドスタート（約 1 秒）がなくなる

### C（同梱）の評価

技術的には可能です。プラグインは Apache-2.0 なので LICENSE / NOTICE を同梱すれば再配布できます。ただし:

- zip が 33MB → 50MB 超になる
- **プラグインの更新を自分で追う必要がある**（SSM 側の仕様追加に追随できないと壊れる）
- CI で MSI から取り出す工程が必要（`msiexec /a` か 7-Zip）
- 実行ファイル同梱物に対する AV の誤検知リスク

→ **「完全ポータブル版」を別配布にする**のが現実的です（通常版は「プラグインを入れてね」）。

## リスクと対策

| リスク | 対策 |
|---|---|
| プラグインの引数仕様が非公開 | 2018 年から aws-cli が使い続けている安定IF。バージョン判定して古ければ警告 |
| 起動失敗時にセッションが残る | 失敗時 `terminate_session()` を呼ぶ（aws-cli も同じ） |
| 引数にトークンが出る | 環境変数方式を使う（`1.2.497.0` 以降） |
| 実機検証ができない | **プラグインを入れないと検証不能**。ここが今回の唯一のブロッカー |

| 注意点 | 内容 |
|---|---|
| **Exec はサービス単位で有効化** | `update-service --enable-execute-command` が必要。**既存タスクには後付け不可**で、有効化すると新デプロイが走ります |

## 原因：PowerShell が「空文字の引数」を落としていた

プラグインには 6 つの引数を渡す必要があります。

| # | 引数 | 正常時 | 実際に渡っていた値 |
|---|---|---|---|
| 1 | セッション情報 | `AWS_SSM_START_SESSION_RESPONSE` | 同じ |
| 2 | リージョン | `ap-northeast-1` | 同じ |
| 3 | 操作名 | `StartSession` | 同じ |
| 4 | プロファイル名 | **`''`（空文字）** | ← **消えた** |

## `prompt_history` について（注意点）

了解です。空ファイルはそのままコミットに含めています。

ただし **1点だけ注意**してください。このファイルはすでに Git の履歴に入っているので、**ここに機密を書いて push してしまうと履歴に残ります**（後から削除しても過去のコミットに残り、GitHub 側のキャッシュにも載ります）。

安全な進め方:

1. ローカルで内容を書く
2. **push する前に** 私に機密部分の削除・マスクを依頼
3. その状態でコミット → push（これなら履歴に残りません）

あるいは、ログは `.gitignore` 済みの場所（例: `.okamo`）に置く運用にすれば、そもそも push されません。必要なら `.gitignore` に `prompt_history` を追加する案もあります（既存の `20260220_claude.txt` は追跡済みなので、その扱いだけ相談）。

内容を書いたら声をかけてください。機密の洗い出しと削除をやります。
